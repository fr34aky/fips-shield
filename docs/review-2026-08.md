# Code review, August 2026 — cost, not shape

A second adversarial review, run across three independent reviewers
(njs engine; eBPF guard and the ban CLIs; nginx templates, fail2ban and
deployment glue) plus behavioural probing of a running stack under the
**shipped defaults** rather than the tightened test policy the suite
uses. Findings marked CONFIRMED were reproduced against that stack and
the reproduction is given; findings marked PLAUSIBLE are traced through
the code but need a runtime check against a real relay.

Nothing here is fixed. Every item is open. As in
[July](review-2026-07.md), reviewer claims that did not survive
verification are recorded under [Non-findings](#non-findings) — one of
them was a HIGH that inverted on measurement, which is the reason that
section exists.

The July review's open items are still open and are not repeated here.

---

## The theme

July found bypasses: ways to get a message *past* the engine. Those are
fixed and I could not reopen them. What this review found instead is
that every control in the shield counts **shape** — messages,
connections, frames, bytes — and none of them prices **cost**. The
detection layer compounds it by firing only on rule violations, so an
attacker who stays inside every configured limit is not merely
tolerated, it is invisible.

The measurement that makes this concrete. One node, shipped defaults,
8 connections (the cap), 4 EVENT/s and 4 REQ/s per connection — 80% of
every limit — where each query is `{"kinds":[1],"limit":10000000}` with
no `since`/`until`:

```text
  duration:            12.1s
  connections:         8 (cap 8), all held open
  messages sent:       1152
  connections cut:     0
  reached the relay:   1152  (95 msg/s)
  uncapped REQs:       384   (32 REQ/s, each asking for up to
                              10,000,000 events)

  shield-verdict lines produced:   0
  non-101 statuses in access log:  0
```

Nothing was violated, so nothing was logged, so fail2ban had nothing to
act on. Every number in that block is inside policy.

## Findings: high

### 1. The njs WebSocket engine costs ~300 µs of worker CPU per byte

**CONFIRMED, measured.** `core/njs/shield_ws.js:377-390` (handshake
accumulator) and `:421` (frame accumulator).

`onData` appends each read to `st.hs` / `st.acc` and reprocesses from
the start: `headerBlockEnd()` (`:102-115`) and `hasBareLf()`
(`:118-125`) rescan from index 0 on every read, and `st.acc` is rebuilt
with `Buffer.concat` per read. The attacker chooses the number of read
events by choosing the segment size, and the cost is paid per read.

Dripping a handshake one byte per read, measuring total nginx worker
CPU inside the container:

| handshake bytes | worker CPU |
|---|---|
| 2000 | 560 ms |
| 4000 | 1110 ms |
| 8000 | 2310 ms |
| 16000 | 4750 ms |

The control experiment is the finding. The same 8000-byte drip against
the `tcp` profile — which runs `js_access` but **no `js_filter`** —
costs **10 ms**, against 2370 ms for the strfry profile on the same
container:

```text
  8000-byte drip -> port 80   strfry (js_filter: WS engine): 2370 ms
  8000-byte drip -> port 2222 tcp (js_access only):            10 ms
```

A 237× amplification attributable to the engine. The same effect holds
after the handshake, inside an established WebSocket, where dripping a
frame payload cost 360 ms for 4000 bytes and 950 ms for 8000 — growing
faster than linearly, because `Buffer.concat` per read is quadratic in
the payload on top of the per-read cost. **Zero verdicts** in both
cases: 16 KB stays under `MAX_HANDSHAKE`, and the frame never completes,
so `takeToken(cfg.bMsg)` in `inspect()` (`:181`) is never reached — all
the expensive work happens before any rate limit applies.

The strfry stream stage has no `limit_conn` (a July open item; here it
is load-bearing), so the only brake is `SHIELD_STRFRY_CONN_RATE=60` per
minute. Sixty 16 KB drips per minute is ~285 CPU-seconds per minute
from one mesh identity sending about a megabyte.

**Fix.** Keep a scan cursor in `st` and scan only newly arrived bytes;
hold `st.acc` as a chunk list with a read offset instead of
concatenating per read; charge the message bucket per frame (or per KB)
rather than only on FIN. Add `limit_conn` to the strfry stream stage.

### 2. Permanent bans are a silent no-op in the file backend

**CONFIRMED, reproduced.** `core/actions/shield-ban:55`, with
`core/njs/shield_core.js:92`.

`until=$(( $(date +%s) + ttl ))` with fail2ban's permanent ban
(`bantime = -1`) writes a timestamp one second in the past, reports
success, and exits 0:

```text
$ shield-ban ban fd97::dead -1
banned fd97::dead until 1785789880      # exit 0
$ cat $SHIELD_BAN_FILE
fd97::dead 1785789880                   # now = 1785789881
$ shield-ban check fd97::dead
not banned fd97::dead                   # exit 1
$ shield-ban list                       # empty
```

Every reader agrees it is not banned: `active_entries` (`:37`), `check`
(`:72`), and `isBanned` (`shield_core.js:92`). July fixed exactly this
for the eBPF backend — `guard/src/main.rs:287` treats `seconds <= 0` as
permanent — and the fix was never carried into the file backend. The
two backends now diverge completely on the same input, so
`SHIELD_BAN_ALSO_FILE=true` leaves nginx's view permanently wrong, and
any operator setting `SHIELD_F2B_BANTIME=-1` gets no enforcement at all.

**Fix.** Mirror the guard: `ttl <= 0` means permanent, stored as `0`;
treat `0` as "never expires" in `active_entries` and `isBanned`. While
there, treat `NaN` from a corrupt line as banned rather than not (a
July open item, same code path).

### 3. Query cost is unbounded, and the complexity metric is inverted

**CONFIRMED.** `core/njs/shield_ws.js:217-237`, `:51`, `:209`, `:253`.

`items` counts filter keys plus array-element counts. That measures how
*enumerated* a query is, not how *selective*. Consequences, all probed
against the running shield and all forwarded to the relay:

- `["REQ","s",{}]` scores **0** and passes. So does `["REQ","s"]` with
  no filter at all (`nFilters = 0`, loop never runs). The broadest
  possible query is the cheapest to pass, while a client asking for 500
  specific ids scores 501 and is cut.
- `limit` is never inspected at any value. `{"kinds":[1],
  "limit":10000000}` scores 3.
- A 100 KB `search` string scores 1 (one key, not an array).
- `NEG-OPEN` carries a filter in `msg[2]` and falls off the end of
  `inspect()`'s branches: no filter-complexity check, no `maxSubs`
  accounting, and priced under the loose `bMsg` bucket (20/s) rather
  than `bReq` (5/s). Negentropy reconciliation over `{}` is the most
  expensive operation strfry offers. `AUTH` is the same shape — a
  schnorr verification priced under `bMsg` rather than `bEvent`.

**Fix.** Require each filter to carry at least one narrowing key
(`ids`/`authors`/`kinds`/`#*`/`since`) and a `limit` at or below a cap;
reject `nFilters === 0`; score `{}` as effectively infinite. Give
`NEG-OPEN` the `REQ` treatment and price `AUTH` under `bEvent`.

### 4. The eBPF ban map fills and never recovers

**CONFIRMED (static).** `guard/bpf/shield_guard.bpf.c:83,86`;
`guard/src/main.rs:299`.

`shield_bans` is `BPF_MAP_TYPE_HASH` (not LRU) with
`max_entries = 65536`. The BPF side only *checks* expiry (`:166`),
never deletes. Userspace prunes only in `cmd_check` (`main.rs:332`) and
`cmd_list` (`:357`), and the shipped action calls neither —
`actionstart`, `actionstop` and `actioncheck` are all empty in
`core/fail2ban/action.d/fips-shield.conf.template:16-18`. In host mode
nothing ever runs `list` or `check`.

Once full, `bpf_map_update_elem` returns `E2BIG`, `cmd_ban` exits 1,
fail2ban logs the failure and does not retry. From then on **no node
can be banned at all, host-wide**, while `fips-guard stats` still shows
drops and everything looks healthy. A mesh identity is a keypair, so
accumulating 65536 of them is cheap.

**Fix.** On `E2BIG`, sweep expired entries and retry once; add a
`prune` verb on a timer; report occupancy as `active/max` in `stats`.

### 5. Detection reads a subset of the signals the shield already writes

**CONFIRMED.** `core/nginx/05-shield-core.stream.template:31-41` vs
`core/fail2ban/jail.d/fips-shield.local.template:13,29,45`.

All three jails tail `shield-*.access.log` and `shield-error.log`. The
stream stage writes `shield-<svc>.stream.log`, which nothing reads. The
stream module has no `limit_conn_status`, so it rejects with a
hard-coded 503 — matching no `failregex`. Therefore every
`MAX_CONNS_PER_NODE` violation is invisible to detection, and the `tcp`
profile, which has no http stage and so no access log at all, has
exactly one ban-able signal: the `conn-rate` verdict.

Worse for the slow cases: on `client_header_timeout` nginx closes the
connection without creating a request object, so **no log line is
written at all**. A node that opens connections and sends nothing is
invisible to every jail. Statuses 400, 408, 413, 414, 494, 499 and 503
likewise match no filter. `client_body_timeout` and `proxy_timeout` are
inactivity timers, not total-duration caps, so a byte every 29 s holds
a connection indefinitely.

**Fix.** Add a jail over `shield-*.stream.log` matching
`"status":(?:503|403),`, and one over the access log for
`(?:400|408|413|414|494)`. Document that idle connections are priced
solely by `limit_conn` — which the strfry stream stage does not have.

### 6. The fail2ban sidecar runs as root with CAP_BPF and the whole bpffs

**CONFIRMED (config); exploitation PLAUSIBLE.**
`deploy/container/compose.guard.yaml:34-48`,
`deploy/container/Dockerfile.fail2ban` (no `USER`),
`compose.yaml:40-49` (no `cap_drop`, no `no-new-privileges`, not
`read_only`).

`CAP_BPF` is host-wide, not shield-scoped: it permits
`BPF_MAP_GET_NEXT_ID` + `BPF_MAP_GET_FD_BY_ID`, i.e. enumerating and
opening **every** BPF map on the host, pinned or not, read and write.
The bind mount is the entire `/sys/fs/bpf` read-write, so the container
can unlink any pin — including all four `shield_*` pins, discarding
every active ban. Within scope it can ban any address, including the
operator's own /128, which per `bpf/shield_guard.bpf.c:4-6` silences
that node against every service on the host.

The container holding this is the one whose entire job is running
fail2ban's regex engine, as root, over attacker-influenced text — and
the compose comment notes the `/mnt/bpf` path was chosen to work around
AppArmor's `docker-default` deny on `/sys/**`, removing the confinement
that would otherwise contain a compromise.

**Fix.** Mount `/sys/fs/bpf/fips-shield` only, read-only (`:ro` still
permits map element updates, so bans keep working while unpinning does
not). Add `cap_drop: [ALL]` and `security_opt: [no-new-privileges:true]`
to both services. At minimum, document that `CAP_BPF` is host-wide.

## Findings: medium

### The connection-rate counter is shared across profiles

**CONFIRMED, reproduced in both directions.** `core/njs/shield_core.js:125`.

```js
var n = dict.incr(s.remoteAddress + ':' + window, 1, 0);
```

The key has no port or service component, so every profile draws on one
budget per node and the tightest limit governs all of them. With
`strfry` at 60/window and `tcp` at 3/window, ten connections to the
relay caused the **first** tcp connection of the window to be refused;
with `tcp` at 50 and `strfry` at 5, twelve cheap tcp connections locked
the node out of the relay entirely:

```text
10 strfry connections, then the 1st tcp connection of the window
  -> 1 x "service":"tcp","layer":"access","rule":"conn-rate"

12 tcp connections, then 2 strfry connections
  -> 2 x "service":"strfry","layer":"access","rule":"conn-rate"
```

This is a different mechanism from July's shared `limit_conn` zones
item, which is about nginx's zones rather than the njs shared dict.
Impact is self-inflicted (the key is per source), but a node that uses
the relay normally can lock itself out of SSH on the same host.

**Fix.** Include the listening port in the key.

### Token buckets are per connection and reset on reconnect

**CONFIRMED, measured.** `core/njs/shield_ws.js:74-76`, constructed
inside `readCfg()` per session.

Opening the concurrency cap's worth of connections and flooding each
admitted **400 events** — 8 × the `SHIELD_WS_EVENT_BURST=50` the knob
implies — before any connection was cut:

```text
connections=8 opened_ok=8 events_admitted=400 distinct_conns_admitting=8
```

Because buckets are rebuilt per session, reconnecting also resets them,
so the real ceiling is `conn_rate × burst` per window rather than
`rate`: 1200 REQ/min per node against the 300/min `ws_req_rate=5`
suggests.

**Fix.** Back the buckets with `ngx.shared` keyed by source, or
document the aggregate ceiling in `shield.env.example`.

### An empty policy value fails open silently

**CONFIRMED, reproduced.** `core/njs/shield_core.js:166,183` and
`:117`.

`banFile: p.ban_file || ''` then `if (!path) return false` means an
empty `ban_file` disables ban enforcement at accept *and* the
mid-session re-check, with no log. Same banlist, same banned address,
only `SHIELD_BAN_FILE` differs:

```text
A) SHIELD_BAN_FILE=/var/lib/fips-shield/banlist
   rendered: ban_file=/var/lib/fips-shield/banlist;
   ::1 is in the banlist -> refused at accept (BANNED)

B) SHIELD_BAN_FILE=            (present but empty)
   rendered: ban_file=;
   ::1 is in the banlist -> HTTP/1.1 502 Bad Gateway   (not enforced)
```

`conn_rate=` behaves the same way via `num('', 0)` and
`if (!cfg.connRate) return false`. A *missing* variable fails closed
instead — see [Non-findings](#non-findings).

**Fix.** Treat an empty `ban_file` as fatal in `access()` (log once and
deny) rather than as "no bans configured".

### Nothing verifies the tc classifier is still attached

**CONFIRMED.** `guard/src/main.rs:317-341`, `:343`, `:367`;
`deploy/host/fips-guard.service:26-27,42-45`.

`check`, `list` and `stats` read only the pinned maps, which by design
outlive the filter (`cmd_unload`'s non-purge path leaves them). If the
classifier is detached — interface recreated, manual `tc filter del` —
`fips-guard check <ip>` still exits 0 and prints "banned until …". There
is no verb that inspects the attachment, so enforcement fails open with
a positive health signal.

Compounding it, the unit's `Restart=on-failure` cannot fire: it is
`Type=oneshot` with `RemainAfterExit=yes`, so after `ExecStart`
succeeds there is no process to restart. The comment above it describes
a recovery path that does not exist.

**Fix.** Add a verb that queries the ingress filter list and exits
non-zero when absent; wire it into `actioncheck` so fail2ban's
`invalidateBanEpoch()` re-bans live tickets after a lost attachment.
Replace `Restart=on-failure` with a path unit or a `Type=simple`
watchdog.

### `SHIELD_GUARD_PIN_DIR` never reaches the action in host mode

**CONFIRMED.** `core/fail2ban/action.d/fips-shield.conf.template:19-20`
vs `guard/src/main.rs:73`.

Exactly the bug July fixed for `SHIELD_BAN_FILE`, one variable over.
Container mode works (the sidecar's environment is inherited); host
mode does not, so `fips-guard load` honours the override while
`shield-ban ban` falls back to `/sys/fs/bpf/fips-shield` and fails on
**every** ban. `SHIELD_GUARD_BIN` and `SHIELD_FILE_BACKEND` have the
same gap.

**Fix.** Pass it explicitly in both action lines and add it to the
`envsubst` lists in `install-fail2ban.sh:50` and `f2b-entrypoint.sh:8`.

### The verdict jail conflates message violations with connection rate

**CONFIRMED.** `core/fail2ban/filter.d/fips-shield-verdict.conf:9`;
`core/njs/shield_core.js:188-192`.

`SHIELD_F2B_VERDICT_MAXRETRY=3` is documented as being for WebSocket
message violations, "each one already cost the client its connection".
The filter matches every rule except `banned`, so it also governs
`conn-rate`. On the tcp profile (`SHIELD_TCP_CONN_RATE=10`) the 11th,
12th and 13th connections in one window are three strikes: **13
connections in a minute earns an hour, doubling toward a week**. An ssh
retry loop does that. The fixed window (`shield_core.js:124`) also lets
a client burn its budget across a boundary.

The intended asymmetry is inverted: the handshake jail tolerates 20
rejections, the verdict jail bans after 3.

**Fix.** Split the filter on the `layer` field, which is already on the
line for this purpose: `layer":"ws` at 3, `layer":"access` higher.

### Remaining medium items

- **`violate()` called from the downstream callback sends the upstream
  Close to the client.** `shield_ws.js:165-169` states the invariant
  "violations only fire inside the 'upstream' callback"; `:467` and
  `:472` break it. On that path the masked client→server Close goes
  downstream and the upstream is never told to close, so it lingers
  until `proxy_timeout` — on the exact path where an uninspected
  upgrade was just detected. CONFIRMED.
- **The downstream callback never checks `st.killed`** (`:462-474`), so
  a session cut for a policy violation keeps receiving relay output
  until `proxy_timeout`. Distinct from July's "killed session never
  propagates EOF". CONFIRMED.
- **The handshake is re-encoded before forwarding** (`:401-404`,
  `:416`): `Buffer → String → Buffer` is not the identity for bytes
  ≥ 0x80, so the block nginx receives can differ in content and length
  from the block validated by `hasBareLf` and the `Upgrade` regex.
  July's "forwarded bytes are never a re-encoding" covers the frame
  path only. ASCII headers round-trip exactly, which is why it has not
  bitten. One-line fix: send `st.hs.slice(0, end)` and keep
  `.toString()` for the regex. CONFIRMED as a defect.
- **`worker_connections` ignores the two-stage design.**
  `core/nginx/nginx.conf:19-23`: a protected client burns four slots
  (stream client, stream→unix, http client, http→app), so a worker tops
  out near 1024 clients, not 4096; and 4096 × 2 fds is the entire
  `worker_rlimit_nofile 8192` budget. At exhaustion nginx stops
  accepting, so `js_access` — and the ban check — never runs. CONFIRMED.
- **The 444 path denial is far cheaper than its comment claims.**
  `41-http.conf.template:72-74` correctly skips `limit_req`, but with
  30 concurrent connections × 100 `keepalive_requests` that is 3000
  unrated requests essentially instantly, 12000/min sustained. Only
  reachable when `SHIELD_HTTP_PATH_REGEX` is narrowed. CONFIRMED.
- **`bantime.increment` state is not persisted in container mode.** The
  jails enable it but `compose.yaml:46-48` never mounts fail2ban's
  `dbfile`, so every `up -d --build` resets escalation to base bantime
  and drops live tickets while the banlist keeps its entries — the
  ticket/banlist desync the guide documents a manual procedure for.
  CONFIRMED.
- **JSON duplicate keys may diverge from the relay's parser.**
  `JSON.parse` is last-key-wins; several C++ relay parsers are
  first-wins. `["EVENT",{"kind":4,"kind":1,…}]` would then be inspected
  as kind 1 and stored as kind 4, defeating the kind denylist; the same
  trick shrinks the filter-complexity count. PLAUSIBLE — needs a probe
  against real strfry. Parser-independent fix: reject any object with a
  duplicate key.
- **UTF-8 decode divergence** in `JSON.parse(buf.toString())`
  (`:186`): if njs's decoder is consuming rather than strict, a lone
  `0xF0` can merge adjacent array elements and undercount
  `maxFilterItems`. PLAUSIBLE — one `njs -e` invocation settles it.
- **Token-bucket refill in BPF underflows on concurrent CPUs.**
  `shield_guard.bpf.c:183-198` mutates a shared (not per-CPU) LRU map
  through a plain pointer with no atomics; an interleaved `last_ns`
  store makes the unsigned `now - b->last_ns` wrap, and
  `elapsed_ms * rate_pps` then overflows — either a full refill every
  packet (throttle bypass) or spurious drops. Distinct from July's
  sub-millisecond-remainder item. CONFIRMED as a defect.
- **The guard has no ordering against the services it protects.**
  `fips-guard.service` has no `Before=`, while `ExecStartPre` waits up
  to 60 s for the interface — so at boot the protected services accept
  mesh traffic before the classifier attaches. CONFIRMED.

## Non-findings

Recorded because they were reported and did not survive verification.

**Container mode does *not* fail open on a missing variable.** The
claim was that `envsubst` renders an unset `SHIELD_*` as empty,
silently disabling ban enforcement. The nginx image's
`20-envsubst-on-templates.sh` builds its substitution list from
variables actually present in the environment, so a **missing**
variable leaves the placeholder literal, nginx reads `${SHIELD_BAN_FILE}`
as a config variable reference, and startup aborts:

```text
2026/08/03 21:00:37 [emerg] 1#1: unknown "shield_ban_file" variable
nginx: [emerg] unknown "shield_ban_file" variable   # exit 1
```

That is failing closed. Only a variable that is *present but empty*
fails open, which is the medium finding above. The distinction matters
because the two have different fixes: a presence check in the
entrypoint would not have caught the real case.

**The handshake scan is not quadratic.** It was reported as O(N²) from
rescanning, with an estimated 10–40 s of CPU for 16 KB. Measured, the
cost is **linear in read events** (2000→16000 bytes is 8× the bytes and
8.5× the CPU). The finding stands — 4.75 s for 16 KB and a 237× control
ratio — but the mechanism is per-read overhead in the njs filter, not
the asymptotics, so a scan cursor alone will not fix it; the per-read
cost has to come down too.

**Shared-dict exhaustion is handled.**
`05-shield-core.stream.template:22` declares both `timeout=` and
`evict`, so `dict.incr` neither throws on a full zone nor accumulates
forever, and the key gives an attacker exactly one entry per window —
they cannot evict other nodes' counters.

## Verified as fine

Re-derived during this review rather than inherited from July.

- **Per-node keying is real.** Previously untestable — every test
  connected from `::1` only, which July called the single largest
  coverage gap. With 44 addresses on the container's loopback:
  exhausting `fd00::a`'s budget did **not** affect `fd00::c`, whose
  first connection was accepted. Limits are genuinely per source /128.
  The caveat is that they bound identities, not operators: 40 fresh
  /128s bought 40 more connections against a per-identity cap of 8, so
  the whole design rests on what a new mesh identity costs.
- **Log injection cannot frame another node**, confirmed independently
  by two reviewers along different paths. nginx's `escape=json` escapes
  quotes, backslashes, control characters and all of 0x80–0xFF; the
  access-log regexes are `^`-anchored; and although the verdict regex is
  unanchored, its only attacker-controlled field passes through njs
  `JSON.stringify`, which escapes `"` → `\"` — the pattern needs an
  unescaped quote that cannot be produced from inside a JSON string.
- **The IPv6 text round-trip is byte-identical** between nginx and
  glibc for every `fd97::/16` address: `ngx_inet6_ntop` initialises
  `max = 1`, so like glibc it refuses to compress a lone zero group,
  emits lowercase with no leading zeros, and picks the first-longest
  run. The assumption at `core/actions/shield-ban:21` holds.
- **WebSocket frame parsing remains correct and strict** — RSV,
  unmasked frames, control-frame limits, `OP_BIN`, unknown opcodes,
  `TEXT`-before-`FIN`, orphan `CONT`, 64-bit lengths, and every partial
  read. Unmasking works on a copy, so forwarded frame bytes are the
  client's originals.
- **The method allowlist cannot be bypassed.** `limit_except` clears
  bits only for known method names, so `FOO` and lowercase `get` land
  in the limited set (403); TRACE and CONNECT are rejected by nginx
  itself (405). Both feed the scan jail.
- **`return 444` really logs 444** — the status is assigned in
  `ngx_http_free_request` before the log handler, despite bypassing the
  special-response handler.
- **eBPF map layout, byte order and clock choice are correct.**
  `Addr6` ↔ `struct addr6` match exactly; the source is read at a fixed
  offset relative to the *network* header, so extension headers,
  fragments and non-TCP traffic all key correctly on both L3 TUN and L2
  devices. `bpf_ktime_get_ns` and `CLOCK_MONOTONIC` are the same clock,
  so an NTP step cannot alter a ban.
- **The full suite passes on a stock kernel**, including the privileged
  guard tests and the containerised fail2ban-through-eBPF path, with
  the L3/TUN shape that matches `fips0`.

## What the shipped defaults actually permit

Per node, strfry profile, before any violation is recorded:

| Control | Value | Aggregate per node |
|---|---|---|
| Concurrent WebSockets | 8 (http stage `limit_conn`) | — |
| Handshakes | 5 r/s, burst 10 | — |
| New TCP connections | 60 / 60 s window | shared with every other profile |
| Messages | 20/s, burst 100 **per connection** | 160/s |
| EVENT | 5/s, burst 50 **per connection** | 40/s (400 measured in burst) |
| REQ + COUNT | 5/s, burst 20 **per connection** | 40/s, each of unbounded cost |
| Subscriptions | 20 **per connection** | 160 |
| `NEG-OPEN` | message bucket only | unpoliced |

Nostr HTTP surface, verified against the running shield: NIP-11 (`GET
/`) returns 200; NIP-86 relay management (`POST /`) is 405; NIP-05,
Blossom and NIP-96 paths are 444. Media services need the `http`
profile with `SHIELD_HTTP_METHODS` and `SHIELD_HTTP_MAX_BODY` widened.
